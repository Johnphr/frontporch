# Front Porch — Architecture (v2)

> **Status:** posting (`linkedapi.ts` + `postGuard.ts`), Apify scraping (`apify.ts`), the
> onboarding call (slice 1) and the story follow-up call (slice 2: story agent + `startCall` story
> branch) are built; memory + feedback (slice 3) too. See [Build order](#build-order).
> [Decisions](#decisions-locked) are locked; change them only by agreeing as a team.
> [Team defaults](#team-defaults-owner-may-change) can be changed by their owner in a PR.

## What we're building

An AI that interviews an older professional by phone and turns their stories
into LinkedIn posts, then uses how readers react to steer the next interview.

```
  ① onboarding call ──► profile + story seeds
            │
            ▼
  ② weekly story call ──► transcript ──► memories + LinkedIn post (auto, fact-checked)
            ▲                                         │
            │                                         ▼
  ④ plan next call ◄── ③ Apify: reactions + comments on his posts,
     (profile + past calls + feedback          + real questions people in his field ask
      + audience questions → questions)
```

1. **Onboarding call:** get to know him: industry, specialty, career arc, story seeds.
2. **Weekly story call:** short open questions, then let him talk (`voice/conversation-guide.md`).
3. **Content:** his stories become LinkedIn posts, using only what he said.
4. **Feedback loop:** reader reactions and comments, plus real audience questions, steer the next call.

No family, no SMS, no UI. Only phone calls in and LinkedIn posts out.

## Decisions (locked)

| Decision | Choice |
|---|---|
| Backend | Everything in Convex: tables, crons, actions, HTTP actions. No separate server |
| UI | None. Setup (his phone, LinkedIn URL, call time) is by hand in the Convex dashboard |
| Phone calls | **Cartesia Managed Agents** run the whole call: phone number, speech-to-text, in-call LLM, voice. No Vapi; no Twilio in our code |
| Agent config | Lives in code (`convex/lib/`), pushed to Cartesia with `npx convex run cartesia:syncAgent` |
| Transcripts | Fetched after the call by polling `GET /agents/calls/{id}` (Cartesia call webhooks aren't available yet) |
| Questions | Generated by the AI each call, from profile + past calls + reader feedback + audience questions |
| Audience questions | Planner input. Reader comments on his posts take priority |
| Posting | Auto-post via LinkedAPI. The post guard fact-checks first; a failing post is held as `needs_review` (`POST_GUARD_MODE=enforce`) until someone runs `linkedapi:approvePost` |
| Feedback | Apify scrapes his posts' reactions + comments |
| Memory | OpenAI `text-embedding-3-small` + Convex vector index (built in slice 3) |
| LLM | Claude `claude-opus-5-5` for planning, profile extraction, writing, fact-checking. The in-call model runs inside Cartesia |
| Build order | Progressive: onboarding first; each slice gives later calls more of the past |

## System

```
             ┌──────────────────────────────────────────────────┐
             │                      Convex                      │
             │ tables · crons · actions · planner · writer      │
             └──┬──────────────▲────────────────┬───────────────┘
   start call   │              │ poll transcript │ actions call out to:
   + per-call   │              │ after the call  │ Claude · OpenAI embeddings
   variables    │              │                 │ LinkedAPI (post)
             ┌──▼──────────────┴──┐              │ Apify (engagement, profile,
             │ Cartesia Managed   │              │        audience questions)
             │ Agent "Pip"        │              ▼
             │ number · STT · LLM │          his LinkedIn
             │ · Sonic voice      │
             └─────────┬──────────┘
                    Grandpa
```

| Step | Direction | Cartesia API |
|---|---|---|
| Prompt, greeting, voice, model | Convex → Cartesia, when the config changes | `PATCH /agents/{agent_id}` |
| Start a call + per-call details | Convex → Cartesia | `POST /agents/calls` with `dynamic_variables` |
| What he said | Cartesia → Convex, after the call | `GET /agents/calls/{id}`: `status`, `transcript[]`, `summary`, `end_reason` |

The phone number is already set up in Cartesia; Convex only needs its id (`CARTESIA_FROM_NUMBER_ID`).

## Flows

### ① Onboarding (slice 1)
1. `cartesia.startCall(elderId)` → `conversation.planNextCall` returns `kind: "onboarding"`
   (no usable profile yet). Optional: `apify.scrapeProfile` → `knownBackground`.
2. Cartesia calls him with the onboarding agent (prompt in `convex/lib/prompts/onboarding.ts`).
3. `cartesia.pollCall` waits for the call to finish, saves the transcript, then
   `pipeline.processCall` → `llm.extractProfile` → `elders.profile` (+ story seeds).
   `stage` becomes `"active"` once the profile is usable; otherwise the next call onboards again.

### ② Weekly story call (slice 2)
1. Hourly cron finds elders whose local `callDay`/`callHour` match → `cartesia.startCall`
   (~1h earlier, `conversation.prepareCall` refreshes the question bank, see below).
2. `cartesia.startCall` (story branch; `reserveCall` picks the kind and refuses if it changed) →
   `conversation.planNextCall` → `{ plan, dynamicVariables }` (kind from PR #7's
   `lib/onboarding.planNextCall`, the same rule `reserveCall` uses): top queued
   question as `mainQuestion`, the next 2–3 as `threads`, memories related to the main question
   (vector search) + people/places, topics to avoid, one `feedback` line saved by the last
   refresh. Fast by design: no Claude call, never waits on a refresh (empty bank → safe opening
   question + a refresh scheduled for next time).
3. Story agent (`CARTESIA_STORY_AGENT_ID`, prompt in `convex/lib/prompts/story.ts`, pushed by
   `cartesia:syncAgent`) gets `dynamicVariables` as Cartesia `dynamic_variables` on
   `POST /agents/calls`. Planning fails → the queued row is marked `failed`, nothing rings.
4. Once a story call is placed, `cartesia.startCall` saves `plan` on the calls row and calls
   `conversation.markPlanUsed({ elderId, bankId: plan.bankId, callId })`.
5. After the call, the post is auto-posted unless `AUTO_POST=off` (tests: the `posts` row stays
   `pending` for `linkedapi:previewPost`; post on purpose with `linkedapi:createPost`).

**Question bank** (`questionBank`, `questionBankMeta`): his ranked next questions, rebuilt by
`conversation.refreshQuestionBank` after every call, when new reader comments arrive, and by
`conversation.prepareCall` ~1h before each call (fresh `apify.findAudienceQuestions` +
`llm.findRecentTopics` web search, run in parallel). Inputs: profile, open threads, memories,
topics covered / to avoid, reader questions (`llm.summarizeFeedback`), audience questions,
recent topics → `llm.planQuestions` writes 8–12 candidates → `lib/planner.ts` ranks them
(open thread > reader > recent topic ≈ audience > memory > profile; avoid topics and questions
asked in recent calls are always skipped; covered topics only for open threads / readers;
dedupes; ages out).

### ③ After the call
`cartesia.pollCall` → `cartesia.applyPoll` saves the normalized transcript
(`lib/cartesia.normalizeTranscript`), summary and `end_reason`, sets `status: "ended"` and
schedules `pipeline.processCall({ callId })`. `processCall` (PR #7) claims the call
(`processingAt`, retaken after 15 min), skips no-conversation calls
(`lib/cartesia.isNoConversation`: voicemail / no answer / busy, or under 30 words from him →
`no_conversation`), then:
- onboarding: `llm.extractProfile` (merged with earlier calls) → `elders.profile`;
  `stage: "active"` once usable · then a question-bank refresh is scheduled (best effort)
- story (each step isolated): `llm.extractKnowledge` → `memories.addMany` (facts, story seeds,
  open threads, people, places, topics covered / to avoid; finished open threads resolved) ·
  `llm.writePost` (may decline: no post) → one `posts` row per call (`by_call`) →
  `linkedapi.createPost` (scheduled, new row only) · `conversation.refreshQuestionBank` (scheduled)

Ends with `status: "done"` + `processedAt`, or `process_failed` + error (claim released, retry
by hand with `pipeline:processCall`; safe: `memories.addMany` skips a callId it already has and
the post row is reused, so no second LinkedIn post).
Inside `linkedapi.createPost`: claim the row (no double posting) → format for LinkedIn
(`lib/linkedinPost.ts`) → `postGuard.checkPost` fact-checks the post against the whole call
and his profile/memories → fail: `needs_review`, nothing posted → pass: LinkedAPI
`st.createPost` → poll → canonical post URL (`lib/linkedinUrl.ts`) saved.

### ④ Feedback loop (slice 3)
Daily cron → `apify.scrapeEngagement` → `engagement.upsert`. The next `planNextCall` reads
`engagement.recentFeedback`; `llm.summarizeFeedback` turns it into "what resonated" + reader
questions worth asking him.

**Audience questions:** weekly `apify.findAudienceQuestions` searches Reddit, Stack Exchange
and (once enabled) Quora and Discourse for real questions people in his field ask, filters,
dedupes and ranks them into `audienceQuestions`. `planNextCall` takes one from
`apify.topAudienceQuestions` and calls `apify.markAudienceQuestionUsed`.

## Build order

| Slice | What works at the end | Context the call uses |
|---|---|---|
| **1 · Onboarding** | Start call → Cartesia call → transcript → profile + story seeds | LinkedIn background (optional) |
| **2 · Story call + post** | Weekly call → post handed to `linkedapi.createPost` | Profile, story seeds, recent call summaries |
| **3 · Memory + feedback** | Vector memory, reader feedback, audience questions in the plan | Everything above + memories, comments, audience questions |

## Data model (in `schema.ts`)

All v2 fields are **optional** (and `calls.callSid` became optional), so v1 rows
still validate. Bookkeeping fields are written by code, never by hand.

```ts
elders:   + stage?: "onboarding" | "active"       // missing = onboarding
          + timezone (IANA), callDay ("sunday"), callHour (0-23 local), linkedinUrl,
          + profile?: { industry?, specialty?, careerSummary?, topics?[], storySeeds?[], topicsToAvoid?[] }
            (all optional, as PR #7 defines it; merged over onboarding calls),
          + knownBackground
          // bookkeeping: lastPreparedSlot, lastCallSlot ("YYYY-MM-DDTHH" local),
          //              lastBankRefreshAt (debounces question-bank refreshes)

calls:    callSid -> optional (v1 only)
          status: queued | in_progress | ended | done | no_conversation | failed |
                  poll_error | poll_timeout | process_failed   (PR #7 lifecycle)
          + kind? ("onboarding" | "story"), cartesiaCallId?, summary?, endReason?, error?,
            pollAttempts?, lastPolledAt?, processingAt? (claim, stale after 15 min),
            processedAt? (set only on success), plan? (CallPlan, Brain)
          indexes by_cartesia, by_elder

memories: elderId, callId?, kind, text, name?, status (active | resolved),
          mentionCount, lastMentionedAt, elderKind (`${elderId}|${kind}`),
          embedding (1536, OpenAI text-embedding-3-small)
          kind: fact | story_seed | open_thread | person | place | topic_covered | avoid
          vectorIndex by_embedding, filterFields [elderId, kind, elderKind]
          (vector filters only do eq/or, so elderKind lets one search mean
           "this elder AND these kinds"); indexes by_elder_kind, by_elder_status,
           by_elder_last, by_call

engagement: elderId, postId?, linkedinUrl (canonical, lib/linkedinUrl.ts), reactions,
            comments [{ author, text }], scrapedAt, changedAt?
            indexes by_elder, by_url, by_elder_scraped, by_elder_changed

posts:    see the Integrations block in schema.ts; + index by_call (one post per call)
audienceQuestions: see the Integrations block in schema.ts.
questionBank: elderId, question, why, source (open_thread | reader | recent_topic | audience |
          memory | profile), sourceRef?, topicKey, priority, firstSeenAt,
          status (queued | used | dropped), usedInCallId?, usedAt?
          indexes by_elder_status_priority, by_elder_status_usedAt   (Core: Brain)
questionBankMeta: elderId, feedbackLine, resonated, refreshedAt; index by_elder
          (what the last refresh worked out; reused by planNextCall and writePost)
```

**Memory functions** (`memories.ts`, all internal):
`addMany({ elderId, callId?, items: [{ kind, text, name? }], resolveThreadIds? })`
→ `{ inserted, merged, resolved }`: embeds, merges near-duplicates (same kind and
similarity ≥ 0.85, or same-named person/place; two different names never merge),
bumps `mentionCount`, keeps the more specific text, marks finished open threads
resolved. A repeat run for a `callId` that already has memories is skipped
(the pipeline also guards with its `processingAt` / `processedAt` claim).
`search({ elderId, text, k, kinds?, includeResolved? })` → `{ _id, kind, text, name?, status, score }[]`.
`listForElder({ elderId, kinds?, status?, limit? })` (newest first, no embeddings).
`resolveThreads({ elderId, ids })`. Prompt text: `formatMemoriesForPrompt` in `lib/memoryText.ts`.

**Engagement** (`engagement.ts`): `upsert` (from `apify.scrapeEngagement`) keeps the
latest snapshot, links `postId` by canonical URL, and when reactions/comments changed
sets `changedAt` and schedules `conversation.refreshQuestionBank` (2 min later, at most
once per elder per 10 min). `commentsKnown: false` (counts-only backup Actor) keeps the
stored comments. `recentFeedback({ elderId, sinceDays? })` →
`{ linkedinUrl, postText?, reactions, comments, scrapedAt, changedAt }[]`, posts whose
reactions/comments changed in the window, most recently changed first.

**Scheduling** (`schedule.ts` + `crons.ts`): hourly `schedule.tick` →
`conversation.prepareCall` about 1 hour before his local call time and
`cartesia.startCall` at the call hour (each local slot once, DST-safe, `lib/schedule.ts`);
daily `apify.scrapeEngagement` and weekly `apify.findAudienceQuestions` for active elders.

**v1 leftovers in `convex/`**: `questions.ts`, `answers.ts`, `replies.ts` (and their tables)
belong to the old product; delete them. `elders.ts`, `calls.ts`, `lib/auth.ts` take a `secret`
argument from the deleted Python server; convert to internal functions. (Core: Data.)

## Going live

1. `npm run deploy` (`npx convex deploy`) creates/updates **production** (separate data + env).
2. Set every env var below on production (`npx convex env set` with `--prod`).
3. `npx convex run --prod cartesia:syncAgent` so the production agent matches the code.
4. Add production grandpa. Run onboarding → story call → post → scrape. Record a backup video.
