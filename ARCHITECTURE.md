## What we're building

An AI that interviews an older professional by phone and turns their stories
into LinkedIn posts, then uses how readers react to steer the next interview.

```
  ① onboarding call ──► profile + first memories
            │
            ▼
  ② weekly story call ──► transcript ──► memories + LinkedIn post (auto)
            ▲                                         │
            │                                         ▼
  ④ plan next call ◄── ③ Apify scrapes reactions + comments on his posts
     (profile + memories + reader feedback → questions)
```

1. **Onboarding call:** get to know him: industry, specialty, career arc, story seeds.
2. **Weekly story call:** the AI asks short open questions and lets him talk (`vapi/conversation-guide.md`).
3. **Content:** his stories become engaging LinkedIn posts, using only what he said.
4. **Feedback loop:** Apify scrapes reactions and comments on his posts. The planner
   uses them for the next call ("A reader asked how you priced bread back then...").

No family, no SMS, no UI. Only phone calls in and LinkedIn posts out.

## Locked so far

| Decision | Choice |
|---|---|
| Backend | Everything in Convex: tables, vector memory, crons, webhook (HTTP action), API calls (actions) |
| UI | None. Setup (his phone, LinkedIn URL, call time) is by hand in the Convex dashboard |
| Questions | Generated by the AI each call, from profile + memories + reader feedback |
| Posting | Auto-post to his LinkedIn via LinkedAPI. No approval step |
| Feedback | Apify scrapes his posts' reactions + comments |
| Memory | Convex vector index, OpenAI `text-embedding-3-small` (1536 dims) |
| LLM | Claude `claude-opus-5-5` for planning + writing; a fast model inside Vapi for the live call |

## Flows

### ① Onboarding (first call)
1. Optional: `apify.scrapeProfile` pulls his LinkedIn work history → `knownBackground`.
2. `vapi.startCall` → `conversation.planNextCall` returns `kind: "onboarding"` →
   onboarding assistant (`vapi/prompts/onboarding.md`).
3. After the call, `pipeline.processCall` runs `llm.extractProfile` → `elders.profile`,
   saves memories, sets `stage: "active"`. No post by default (open decision 3).

### ② Weekly story call
1. Hourly cron finds elders whose local `callDay`/`callHour` match → `vapi.startCall`.
2. `conversation.planNextCall`: profile + top memories + summarized reader feedback →
   `llm.planQuestions` → `mainQuestion` + 2–3 backup `threads`.
3. Story assistant (`vapi/prompts/story-call.md`) gets the plan as variables.

### ③ After the call
Vapi `end-of-call-report` → `/vapi/webhook` → `pipeline.processCall`:
save transcript → extract memories → `llm.writePost` → `posts` row →
`linkedapi.createPost` → post URL saved on the row.

### ④ Feedback loop
Daily cron → `apify.scrapeEngagement` (his recent posts with reactions + comments) →
`engagement.upsert`. The next `planNextCall` reads `engagement.recentFeedback`, and
`llm.summarizeFeedback` turns it into "what resonated" + reader questions worth asking him.

## Contracts (agree on these first, then work in parallel)

```ts
type CallPlan = {                  // conversation.planNextCall -> vapi.startCall
  kind: "onboarding" | "story";
  mainQuestion?: string;
  threads: string[];               // backup topics
  memories: string[];
  feedback?: string;               // one short line Pip reads out
  knownBackground?: string;        // onboarding only
};

type CallResult = {                // vapi.webhook -> pipeline.processCall
  vapiCallId: string;
  elderId: Id<"elders">;
  kind: "onboarding" | "story";
  turns: { role: "pip" | "elder"; text: string }[];
  summary?: string;
  endedReason: string;             // "customer-ended-call", "voicemail", ...
};
```

**Vapi metadata** (set at call start, read back in the webhook): `{ elderId, kind }`.
**Prompt variables**: the `{{...}}` names listed at the top of each `vapi/prompts/*.md`.

**Function names** (all `internal.*`):
`vapi.startCall` · `conversation.planNextCall` · `pipeline.processCall` ·
`llm.writePost` · `llm.extractMemories` · `llm.extractProfile` · `llm.summarizeFeedback` ·
`llm.planQuestions` · `memories.add` · `memories.search` · `engagement.upsert` ·
`engagement.recentFeedback` · `apify.scrapeEngagement` · `apify.scrapeProfile` ·
`linkedapi.createPost`

## Data model (draft, not in `schema.ts` yet)

```ts
elders: defineTable({
  name: v.string(), phone: v.string(),          // E.164
  language: v.string(),                         // BCP-47, e.g. en-US
  timezone: v.string(), callDay: v.string(), callHour: v.number(),
  linkedinUrl: v.optional(v.string()),
  stage: v.union(v.literal("onboarding"), v.literal("active")),
  profile: v.optional(v.object({
    industry: v.string(), specialty: v.string(), careerSummary: v.string(),
    topicsToAvoid: v.array(v.string()),
  })),
}).index("by_phone", ["phone"]),

calls: defineTable({
  elderId: v.id("elders"), kind: v.string(),    // onboarding | story
  vapiCallId: v.optional(v.string()), status: v.string(),
  plan: v.optional(v.any()),                    // CallPlan, for debugging
  transcript: v.array(v.object({ role: v.string(), text: v.string() })),
  summary: v.optional(v.string()), endedReason: v.optional(v.string()),
}).index("by_vapi", ["vapiCallId"]).index("by_elder", ["elderId"]),

memories: defineTable({
  elderId: v.id("elders"), callId: v.optional(v.id("calls")),
  text: v.string(), embedding: v.array(v.float64()),
}).vectorIndex("by_embedding", { vectorField: "embedding", dimensions: 1536,
                                 filterFields: ["elderId"] }),

posts: defineTable({
  elderId: v.id("elders"), callId: v.id("calls"),
  text: v.string(), status: v.string(),         // pending | published | failed
  linkedinUrl: v.optional(v.string()), error: v.optional(v.string()),
}).index("by_elder", ["elderId"]).index("by_url", ["linkedinUrl"]),

engagement: defineTable({
  elderId: v.id("elders"), postId: v.optional(v.id("posts")),
  linkedinUrl: v.string(), reactions: v.number(),
  comments: v.array(v.object({ author: v.string(), text: v.string() })),
  scrapedAt: v.number(),
}).index("by_elder", ["elderId"]).index("by_url", ["linkedinUrl"]),
```

**v1 leftovers in `convex/`**: `questions.ts`, `answers.ts`, `replies.ts` (and their
tables) belong to the old "answer internet questions" product. Delete them.
`elders.ts`, `calls.ts`, `lib/auth.ts` take a `secret` argument from the deleted
Python server; convert to internal functions. Core: Data does this in its first PR.

## Going live

1. `npm run deploy` (`npx convex deploy`) creates/updates **production**.
   Its database and env vars are separate from dev.
2. Set every env var below on production (`npx convex env set` with `--prod`).
3. Point both Vapi assistants' server URL at the production `.convex.site/vapi/webhook`.
4. Seed production grandpa. Run onboarding → story call → post → scrape. Record a backup video.

During development, everyone gets their own dev deployment from `npx convex dev`, but
Vapi can only call one webhook URL. Use one shared dev deployment for call testing.
