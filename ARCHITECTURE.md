# Front Porch — Architecture (v2)

> **Status:** posting (`linkedapi.ts` + `postGuard.ts`), Apify scraping (`apify.ts`), the
> onboarding call (slice 1) and the story follow-up call (slice 2: story agent + `startCall` story
> branch) are built; memory + feedback (slice 3) too. See [Build order](#build-order).
> [Decisions](#decisions-locked) are locked; change them only by agreeing as a team.
> [Team defaults](#team-defaults-owner-may-change) can be changed by their owner in a PR.

## What we're building

An AI that interviews an older professional by phone and turns their stories
into LinkedIn posts, then uses how readers react to steer the next interview.

```
  ① onboarding call ──► profile + story seeds
            │
            ▼
  ② weekly story call ──► transcript ──► memories + LinkedIn post (auto, fact-checked)
            ▲                                         │
            │                                         ▼
  ④ plan next call ◄── ③ Apify: reactions + comments on his posts,
     (profile + past calls + feedback          + real questions people in his field ask
      + audience questions → questions)
```

1. **Onboarding call:** get to know him: industry, specialty, career arc, story seeds.
2. **Weekly story call:** short open questions, then let him talk (`voice/conversation-guide.md`).
3. **Content:** his stories become LinkedIn posts, using only what he said.
4. **Feedback loop:** reader reactions and comments, plus real audience questions, steer the next call.

No family, no SMS. One small onboarding UI (`frontend/onboarding-ui/`); everything else is phone calls in and LinkedIn posts out.

## System

```
             ┌──────────────────────────────────────────────────┐
             │                      Convex                      │
             │ tables · crons · actions · planner · writer      │
             └──┬──────────────▲────────────────┬───────────────┘
   start call   │              │ poll transcript │ actions call out to:
   + per-call   │              │ after the call  │ OpenAI LLM + embeddings
   variables    │              │                 │ LinkedAPI (post)
             ┌──▼──────────────┴──┐              │ Apify (engagement, profile,
             │ Cartesia Managed   │              │        audience questions)
             │ Agent per character│              ▼
             │ number · STT · LLM │          his LinkedIn
             │ · Sonic voice      │
             └─────────┬──────────┘
                    Grandpa
```

| Step | Direction | Cartesia API |
|---|---|---|
| Prompt, greeting, voice, model | Convex → Cartesia, when the config changes | `PATCH /agents/{agent_id}` |
| Start a call + per-call details | Convex → Cartesia | `POST /agents/calls` with `dynamic_variables` |
| What he said | Cartesia → Convex, after the call | `GET /agents/calls/{id}`: `status`, `transcript[]`, `summary`, `end_reason` |

The phone number is already set up in Cartesia; Convex only needs its id (`CARTESIA_FROM_NUMBER_ID`).

## Flows

### ① Onboarding (slice 1)
1. `cartesia.startCall(elderId)` → `conversation.planNextCall` returns `kind: "onboarding"`
   (no usable profile yet). Optional: `apify.scrapeProfile` → `knownBackground`.
2. Cartesia calls him with his character's agent and the onboarding goal (prompt in
   `convex/lib/prompts/agent.ts`).
3. `cartesia.pollCall` waits for the call to finish, saves the transcript, then
   `pipeline.processCall` → `llm.extractProfile` → `elders.profile` (+ story seeds).
   `stage` becomes `"active"` once the profile is usable; otherwise the next call onboards again.

### ② Weekly story call (slice 2)
1. Hourly cron finds elders whose local `callDay`/`callHour` match → `cartesia.startCall`
   (~1h earlier, `conversation.prepareCall` refreshes the question bank, see below).
2. `cartesia.startCall` (story branch; `reserveCall` picks the kind and refuses if it changed) →
   `conversation.planNextCall` → `{ plan, dynamicVariables }` (kind from PR #7's
   `lib/onboarding.planNextCall`, the same rule `reserveCall` uses). **One simple goal**: a story
   that starts from today's `question` (top queued bank row), plus context: memories related to
   it (vector search, capped at 10 s) + people/places, topics to avoid, one `feedback` line saved
   by the last refresh. Fast by design: no LLM call, never waits on a refresh (empty bank →
   safe default question + a refresh scheduled for next time).
3. His character's agent (id from the `characterAgents` table; prompt in
   `convex/lib/prompts/agent.ts`, pushed by `cartesiaAgents:syncAgent`) gets `dynamicVariables`
   (`first_name`, `goal`, `context`) as Cartesia `dynamic_variables` on `POST /agents/calls`. Planning fails → the queued row is marked `failed`, nothing rings.
4. Once a story call is placed, `cartesia.startCall` saves `plan` on the calls row and calls
   `conversation.markPlanUsed({ elderId, bankId: plan.bankId, callId })`.
5. After the call, the post is auto-posted unless `AUTO_POST=off` (tests: the `posts` row stays
   `pending` for `linkedapi:previewPost`; post on purpose with `linkedapi:createPost`).

**Question bank** (`questionBank`, `questionBankMeta`): his ranked next questions, rebuilt by
`conversation.refreshQuestionBank` after every call, when new reader comments arrive, and by
`conversation.prepareCall` ~1h before each call (fresh `apify.findAudienceQuestions` +
`llm.findRecentTopics` web search, run in parallel). Inputs: profile, open threads, memories,
topics covered / to avoid, reader questions (`llm.summarizeFeedback`), audience questions,
recent topics → `llm.planQuestions` writes 8–12 candidates → `lib/planner.ts` ranks them
(open thread > reader > recent topic ≈ audience > memory > profile; avoid topics and questions
asked in recent calls are always skipped; covered topics only for open threads / readers;
dedupes; ages out).

### ③ After the call
`cartesia.pollCall` → `cartesia.applyPoll` saves the normalized transcript
(`lib/cartesia.normalizeTranscript`), summary and `end_reason`, sets `status: "ended"` and
schedules `pipeline.processCall({ callId })`. `processCall` (PR #7) claims the call
(`processingAt`, retaken after 15 min), skips no-conversation calls
(`lib/cartesia.isNoConversation`: voicemail / no answer / busy, or under 30 words from him →
`no_conversation`), then:
- onboarding: `llm.extractProfile` (merged with earlier calls) → `elders.profile`;
  `stage: "active"` once usable · then a question-bank refresh is scheduled (best effort)
- story (each step isolated): `llm.extractKnowledge` → `memories.addMany` (facts, story seeds,
  open threads, people, places, topics covered / to avoid; finished open threads resolved) ·
  `llm.writePost` (may decline: no post) → one `posts` row per call (`by_call`) →
  `linkedapi.createPost` (scheduled, new row only) · `conversation.refreshQuestionBank` (scheduled)

Ends with `status: "done"` + `processedAt`, or `process_failed` + error (claim released, retry
by hand with `pipeline:processCall`; safe: `memories.addMany` skips a callId it already has and
the post row is reused, so no second LinkedIn post).
Inside `linkedapi.createPost`: claim the row (no double posting) → format for LinkedIn
(`lib/linkedinPost.ts`) → `postGuard.checkPost` fact-checks the post against the whole call
and his profile/memories → fail: `needs_review`, nothing posted → pass: LinkedAPI
`st.createPost` → poll → canonical post URL (`lib/linkedinUrl.ts`) saved.

### ④ Feedback loop (slice 3)
Daily cron → `schedule.dailyEngagement` → `blueskyEngagement.scrapeForElder` per active elder
(staggered 30 s). For each Bluesky thread he posted in the last 30 days (`postPublications`
rows that are `posted` and not removed), one `app.bsky.feed.getPostThread` (depth 6) on the
public AppView, no login; only if that fails (not "deleted") it retries through his PDS with his
session. From the thread (`lib/blueskyEngagement.ts`): likes + reposts summed over HIS posts →
`reactions`; replies by OTHER accounts (author did ≠ the root uri's repo; blocked, deleted and
not-found posts skipped; max 20, 500 chars each) → `comments` as `{ author: "Name (@handle)", text }`.
Each thread → `engagement.upsert` with `platform: "bluesky"` and its `postId`; one failing
thread doesn't stop the others. LinkedIn (`apify.scrapeEngagement`, Apify) runs too only when
`LINKEDIN_POSTING=on`.

When a row's numbers or replies changed, `upsert` schedules `conversation.refreshQuestionBank`
(debounced). It reads `engagement.recentFeedback` (both platforms; posts taken down are left
out); `llm.summarizeFeedback` turns replies into "what resonated" + reader questions for the
bank + the one line Pip reads him ("A reader asked how you priced bread back then...").

**Audience questions:** weekly `apify.findAudienceQuestions` searches Reddit, Stack Exchange,
Bluesky (with his login) and (once enabled) Quora and Discourse for real questions people in his field ask, filters,
dedupes and ranks them into `audienceQuestions`. `planNextCall` takes one from
`apify.topAudienceQuestions` and calls `apify.markAudienceQuestionUsed`.

**Thread replies:** when the call's question came from a Bluesky or Reddit thread,
`pipeline.processCall`'s `reply` step schedules `threadReplies.draftForCall`:
`replyWriter.writeReply` (his words, first person, from his own account) -> AI disclosure line ->
`postGuard.checkPost` -> one row per thread in `threadReplies`. Bluesky posts automatically
(`threadReplies.postReply`); Reddit only with `REDDIT_POSTING=on` + approved API credentials.
Every other source (Quora, Discourse, Stack Exchange) gets no reply and no row. Setup:
convex/README.md "Thread replies".

### ⑤ He calls in (inbound)
Our one number routes to one Cartesia agent: the bilingual inbound agent
(`lib/prompts/inbound.ts`). Cartesia has no pre-call hook, so it greets generically and first
calls the `lookup_caller` webhook tool (filled from `system__caller_id` +
`system__conversation_id`) → `POST /cartesia/inbound-lookup` (`http.ts`, bearer
`CARTESIA_TOOL_SECRET`) → `inbound.handleLookup`: elder by phone → same plan as outbound
(onboarding or `conversation.planNextCall`), `calls` row `direction: "inbound"`, `markPlanUsed`,
`cartesia.pollCall` → `pipeline.processCall`. Unknown number → polite goodbye, nothing revealed,
no row. Backstop: `inbound.syncInboundCalls` every 10 min lists the agent's recent calls
(`GET /agents/calls`) and records finished ones from elders that have no row.

### ⑥ Undo: taking a post back
Posting is automatic, so undo is the safety valve. `convex/undo.ts` (rules: `lib/undo.ts`,
Bluesky deletes: `lib/blueskyDelete.ts`), internal functions only:
- `undo.removePost({ postId, reason? })` → `{ removed, failed, manual, waiting }`. Sets
  `posts.removedAt` / `removedReason` / `status: "removed"` first (publishing never sends a post
  with `removedAt`), then each `postPublications` row: `pending` / `failed` / `skipped` →
  `removed`; `posted` / `maybe_posted` → claimed as `removing` → deleted → `removed` (on failure:
  back to its status with a short error, listed in `failed`); `posting` → left alone (the
  publisher re-checks `removedAt` after posting and calls `removePost` again). Bluesky:
  `com.atproto.repo.deleteRecord` for every post of the thread, replies first, root last (only
  records in his own repo; already gone = success). Reddit: `POST /api/del`. LinkedIn: no delete
  through LinkedAPI → `manual` with the link; after removing it by hand,
  `undo.markRemovedByHand`. Safe to run twice.
- `undo.removeReply({ replyId })`: the same for a thread reply (Bluesky `postedUri`, or his reply
  found under the question post on older rows; Reddit by the comment's fullname from its link).
  A reply that was taken down, or whose call's post was, is never posted (`claimReply`); one taken
  down mid-post is removed right after (`finishReply`).
- `undo.removeLatest({ elderId, reason?, askedOnCallId? })`: his newest post that went out in
  the last 14 days, plus the thread replies from that call. An already-removed newest post still
  counts, so asking twice never reaches back to an older post.

**By phone.** Every character's prompt (and the inbound agent's) says: if he asks to take a
post down, never argue; confirm which one ("the one about…?"), then say a fixed line ("I'll
have it taken down right after our call"). After the call, `pipeline.processCall` runs one
isolated step before anything else (so even a 20-second "please take that down" call counts):
`lib/undo.detectTakeDown` reads the transcript and, on a clear request (or a vague one Pip
committed to), schedules `undo.removeLatest` with `askedOnCallId` (never that call's own post,
never anything newer than the call). A mid-call webhook tool was not built: the outbound agents
have no tools, and Cartesia doesn't document that `system__conversation_id` matches our
`cartesiaCallId`, so we couldn't tie a tool request to the elder reliably.

**By command (family / admin):** `npx convex run undo:removePost '{"postId":"..."}'` (or
`undo:removeLatest '{"elderId":"..."}'`). `lib/undo.postUndoInfo` renders the command and a
status line for the /posts page.

| Slice | What works at the end | Context the call uses |

## Data model (in `schema.ts`)

All v2 fields are **optional** (and `calls.callSid` became optional), so v1 rows
still validate. Bookkeeping fields are written by code, never by hand.

```ts
elders:   + stage?: "onboarding" | "active"       // missing = onboarding
          + timezone (IANA), callDay ("sunday"), callHour (0-23 local), linkedinUrl,
          + profile?: { industry?, specialty?, careerSummary?, topics?[], storySeeds?[], topicsToAvoid?[] }
            (all optional, as PR #7 defines it; merged over onboarding calls),
          + knownBackground
          + characterId? (lib/characters.ts; missing = default for his language)
          // bookkeeping: lastPreparedSlot, lastCallSlot ("YYYY-MM-DDTHH" local),
          //              lastBankRefreshAt (debounces question-bank refreshes)

calls:    callSid -> optional (v1 only)
          status: queued | in_progress | ended | done | no_conversation | failed |
                  poll_error | poll_timeout | process_failed   (PR #7 lifecycle)
          + kind? ("onboarding" | "story"), cartesiaCallId?, summary?, endReason?, error?,
            pollAttempts?, lastPolledAt?, processingAt? (claim, stale after 15 min),
            processedAt? (set only on success), plan? (CallPlan, Brain)
          indexes by_cartesia, by_elder

memories: elderId, callId?, kind, text, name?, status (active | resolved),
          mentionCount, lastMentionedAt, elderKind (`${elderId}|${kind}`),
          embedding (1536, OpenAI text-embedding-3-small)
          kind: fact | story_seed | open_thread | person | place | topic_covered | avoid
          vectorIndex by_embedding, filterFields [elderId, kind, elderKind]
          (vector filters only do eq/or, so elderKind lets one search mean
           "this elder AND these kinds"); indexes by_elder_kind, by_elder_status,
           by_elder_last, by_call

engagement: elderId, postId?, platform? (linkedin | bluesky; missing = linkedin),
            linkedinUrl (the post's link on its platform: LinkedIn canonical via
            lib/linkedinUrl.ts; Bluesky the thread's bsky.app link), reactions,
            comments [{ author, text }], scrapedAt, changedAt?
            indexes by_elder, by_url, by_elder_scraped, by_elder_changed

posts:    see the Integrations block in schema.ts; + index by_call (one post per call)
audienceQuestions: see the Integrations block in schema.ts.
questionBank: elderId, question, why, source (open_thread | reader | recent_topic | audience |
          memory | profile), sourceRef?, topicKey, priority, firstSeenAt,
          status (queued | used | dropped), usedInCallId?, usedAt?
          indexes by_elder_status_priority, by_elder_status_usedAt   (Core: Brain)

          (what the last refresh worked out; reused by planNextCall and writePost)
```

**Memory functions** (`memories.ts`, all internal):
`addMany({ elderId, callId?, items: [{ kind, text, name? }], resolveThreadIds? })`
→ `{ inserted, merged, resolved }`: embeds, merges near-duplicates (same kind and
similarity ≥ 0.85, or same-named person/place; two different names never merge),
bumps `mentionCount`, keeps the more specific text, marks finished open threads
resolved. A repeat run for a `callId` that already has memories is skipped
(the pipeline also guards with its `processingAt` / `processedAt` claim).
`search({ elderId, text, k, kinds?, includeResolved? })` → `{ _id, kind, text, name?, status, score }[]`.
`listForElder({ elderId, kinds?, status?, limit? })` (newest first, no embeddings).
`resolveThreads({ elderId, ids })`. Prompt text: `formatMemoriesForPrompt` in `lib/memoryText.ts`.

**Engagement** (`engagement.ts`): `upsert` (from `blueskyEngagement.scrapeForElder` and
`apify.scrapeEngagement`) keeps the latest snapshot per post per platform, links `postId`
(Bluesky: passed in from `postPublications`; LinkedIn: by canonical URL), and when reactions/comments changed
sets `changedAt` and schedules `conversation.refreshQuestionBank` (2 min later, at most
once per elder per 10 min). `commentsKnown: false` (counts-only backup Actor) keeps the
stored comments. `recentFeedback({ elderId, sinceDays? })` →
`{ linkedinUrl, platform, postText?, reactions, comments, scrapedAt, changedAt }[]`, posts whose
reactions/comments changed in the window, most recently changed first.

**Scheduling** (`schedule.ts` + `crons.ts`): hourly `schedule.tick` →
`conversation.prepareCall` about 1 hour before his local call time and
`cartesia.startCall` at the call hour (each local slot once, DST-safe, `lib/schedule.ts`);
daily `blueskyEngagement.scrapeForElder` (+ `apify.scrapeEngagement` when `LINKEDIN_POSTING=on`)
and weekly `apify.findAudienceQuestions` for active elders.

**v1 leftovers in `convex/`** (done): `questions.ts`, `answers.ts`, `replies.ts`, `calls.ts` and
`lib/auth.ts` are deleted; `elders.ts` keeps only the internal `seed`. The **only public Convex
functions are `signup.*`** (the sign-up page): anyone with the deployment URL can call public
ones, and the v1 dashboard queries exposed call transcripts. `signup.*` return only ids and
ok/reason results. Keep every other function `internal*`. The v1 `questions`, `answers`
and `replies` tables stay in `schema.ts` until they're empty, so a deploy can't fail on old rows.

## Accounts (his own Bluesky, from sign-up)

Each elder posts from **his own** account, connected on the sign-up page (step 4, "Connect Bluesky").

- **Connect:** `signup:connectBluesky({ elderId, token, handle, appPassword })` (action). The handle is tidied (`@` stripped, lowercase, `.bsky.social` added when there's no dot). Only an **app password** (`xxxx-xxxx-xxxx-xxxx`) is accepted, never his real one: an app password can't change his password or delete his account, and he can revoke it in Bluesky. It logs in once (`lib/blueskyClient.createSession`) to prove it works; a session whose token scope says "main password" is refused too. Then it saves the handle, DID and the **encrypted** app password. Results are codes only (`{ ok, handle }` or `{ ok: false, error }`); the password is never echoed or logged. Rate limit: 5 tries an hour, 5 s apart (`lib/signupRules.connectRateLimit`). Locked once he's `active`, like `setLinkedin` was.
- **Storage:** `elderAccounts` (one row per elder + platform; `status` connected / invalid / disconnected). The secret is AES-256-GCM (`lib/accountCrypto.ts`, Web Crypto) with a random IV, and the elderId + platform as additional data, so a ciphertext copied to another elder's row won't decrypt. Key: env `ACCOUNTS_ENC_KEY`; missing or malformed is a clear error, never a plaintext fallback.
- **Use:** every caller gets his login from `lib/logins.ts` (`blueskyLoginForElder(ctx, elderId)`), which reads the row with `accounts:getForLogin` and **decrypts inside the caller's action**. No query or mutation decrypts, and no function returns a plaintext secret. `accounts:status` shows what's connected, with no secret. When Bluesky refuses his saved login, callers can pass the error to `logins.reportBlueskyLoginError(ctx, elderId, error)`, which marks the account `invalid` (`accounts:markInvalid`). `accounts:disconnect` drops the secret.
- **Demo account:** `BLUESKY_HANDLE` / `BLUESKY_APP_PASSWORD` are used only when `DEMO_ACCOUNT_FALLBACK=on` and he has no connected account (or in pure tests with no ctx and no elder). If he has an account that won't decrypt, the result is null, never the demo account.
- **Reddit:** coming soon (shown disabled on the sign-up page). There is no per-elder Reddit connect yet; `redditLoginForElder` returns the env account only with `REDDIT_POSTING=on` **and** `DEMO_ACCOUNT_FALLBACK=on`.
- **Limits:** accounts on a PDS other than bsky.social need `BLUESKY_SERVICE` (we don't resolve his PDS from his DID yet).

**Sign-up token.** `signup:register` (an action) creates his row and returns a random token (32 bytes, base64url); only its SHA-256 hash is stored (`elders.signupTokenHash`). `setCharacter`, `connectBluesky`, `setLinkedin` and `requestCall` all need it (constant-time hash compare), so knowing his phone number or elderId isn't enough to change his sign-up. A number that's already signed up gets no id and no token: re-issuing one would hand it to whoever types his number. The page keeps the token in `sessionStorage`. `register` also sets his weekly slot so `schedule.tick` can call him: `timezone` from the browser (checked with Intl; else from the phone's country: MX → America/Mexico_City, ES → Europe/Madrid, otherwise America/Los_Angeles), `callDay` = the sign-up weekday in that zone, `callHour` = 10.

## Going live

1. `npm run deploy` (`npx convex deploy`) creates/updates **production** (separate data + env).
2. Set every env var below on production (`npx convex env set` with `--prod`).
3. `npx convex run --prod cartesiaAgents:syncAgent` so production has one agent per character, matching the code.
4. Add production grandpa. Run onboarding → story call → post → scrape. Record a backup video.
