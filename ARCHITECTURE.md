# Front Porch — Architecture (v2)

> **Status:** posting (`linkedapi.ts` + `postGuard.ts`) and Apify scraping (`apify.ts`) are
> built. The conversation side is being built in slices (see [Build order](#build-order)).
> [Decisions](#decisions-locked) are locked; change them only by agreeing as a team.
> [Team defaults](#team-defaults-owner-may-change) can be changed by their owner in a PR.

## What we're building

An AI that interviews an older professional by phone and turns their stories
into LinkedIn posts, then uses how readers react to steer the next interview.

```
  ① onboarding call ──► profile + story seeds
            │
            ▼
  ② weekly story call ──► transcript ──► memories + LinkedIn post (auto, fact-checked)
            ▲                                         │
            │                                         ▼
  ④ plan next call ◄── ③ Apify: reactions + comments on his posts,
     (profile + past calls + feedback          + real questions people in his field ask
      + audience questions → questions)
```

1. **Onboarding call:** get to know him: industry, specialty, career arc, story seeds.
2. **Weekly story call:** short open questions, then let him talk (`voice/conversation-guide.md`).
3. **Content:** his stories become LinkedIn posts, using only what he said.
4. **Feedback loop:** reader reactions and comments, plus real audience questions, steer the next call.

No family, no SMS, no UI. Only phone calls in and LinkedIn posts out.

## Decisions (locked)

| Decision | Choice |
|---|---|
| Backend | Everything in Convex: tables, crons, actions, HTTP actions. No separate server |
| UI | None. Setup (his phone, LinkedIn URL, call time) is by hand in the Convex dashboard |
| Phone calls | **Cartesia Managed Agents** run the whole call: phone number, speech-to-text, in-call LLM, voice. No Vapi; no Twilio in our code |
| Agent config | Lives in code (`convex/lib/`), pushed to Cartesia with `npx convex run cartesia:syncAgent` |
| Transcripts | Fetched after the call by polling `GET /agents/calls/{id}` (Cartesia call webhooks aren't available yet) |
| Questions | Generated by the AI each call, from profile + past calls + reader feedback + audience questions |
| Audience questions | Planner input. Reader comments on his posts take priority |
| Posting | Auto-post via LinkedAPI. The post guard fact-checks first; a failing post is held as `needs_review` (`POST_GUARD_MODE=enforce`) until someone runs `linkedapi:approvePost` |
| Feedback | Apify scrapes his posts' reactions + comments |
| Memory | OpenAI `text-embedding-3-small` + Convex vector index (built in slice 3) |
| LLM | Claude `claude-opus-5-5` for planning, profile extraction, writing, fact-checking. The in-call model runs inside Cartesia |
| Build order | Progressive: onboarding first; each slice gives later calls more of the past |

## System

```
             ┌──────────────────────────────────────────────────┐
             │                      Convex                      │
             │ tables · crons · actions · planner · writer      │
             └──┬──────────────▲────────────────┬───────────────┘
   start call   │              │ poll transcript │ actions call out to:
   + per-call   │              │ after the call  │ Claude · OpenAI embeddings
   variables    │              │                 │ LinkedAPI (post)
             ┌──▼──────────────┴──┐              │ Apify (engagement, profile,
             │ Cartesia Managed   │              │        audience questions)
             │ Agent "Pip"        │              ▼
             │ number · STT · LLM │          his LinkedIn
             │ · Sonic voice      │
             └─────────┬──────────┘
                    Grandpa
```

| Step | Direction | Cartesia API |
|---|---|---|
| Prompt, greeting, voice, model | Convex → Cartesia, when the config changes | `PATCH /agents/{agent_id}` |
| Start a call + per-call details | Convex → Cartesia | `POST /agents/calls` with `dynamic_variables` |
| What he said | Cartesia → Convex, after the call | `GET /agents/calls/{id}`: `status`, `transcript[]`, `summary`, `end_reason` |

The phone number is already set up in Cartesia; Convex only needs its id (`CARTESIA_FROM_NUMBER_ID`).

## Flows

### ① Onboarding (slice 1)
1. `cartesia.startCall(elderId)` → `conversation.planNextCall` returns `kind: "onboarding"`
   (no usable profile yet). Optional: `apify.scrapeProfile` → `knownBackground`.
2. Cartesia calls him with the onboarding agent (prompt in `convex/lib/prompts/onboarding.ts`).
3. `cartesia.pollCall` waits for the call to finish, saves the transcript, then
   `pipeline.processCall` → `llm.extractProfile` → `elders.profile` (+ story seeds).
   `stage` becomes `"active"` once the profile is usable; otherwise the next call onboards again.

### ② Weekly story call (slice 2)
1. Hourly cron finds elders whose local `callDay`/`callHour` match → `cartesia.startCall`.
2. `conversation.planNextCall`: profile + story seeds + recent call summaries (slice 2), then
   memories + reader feedback + audience questions (slice 3) → `llm.planQuestions`.
3. Story agent (draft prompt: `voice/prompts/story-call.md`) gets the plan as dynamic variables.

### ③ After the call
`cartesia.pollCall` → `pipeline.processCall`: save transcript → extract memories →
`llm.writePost` → `posts` row → `linkedapi.createPost`.
Inside `linkedapi.createPost`: claim the row (no double posting) → format for LinkedIn
(`lib/linkedinPost.ts`) → `postGuard.checkPost` fact-checks the post against the whole call
and his profile/memories → fail: `needs_review`, nothing posted → pass: LinkedAPI
`st.createPost` → poll → canonical post URL (`lib/linkedinUrl.ts`) saved.

### ④ Feedback loop (slice 3)
Daily cron → `apify.scrapeEngagement` → `engagement.upsert`. The next `planNextCall` reads
`engagement.recentFeedback`; `llm.summarizeFeedback` turns it into "what resonated" + reader
questions worth asking him.

**Audience questions:** weekly `apify.findAudienceQuestions` searches Reddit, Stack Exchange
and (once enabled) Quora and Discourse for real questions people in his field ask, filters,
dedupes and ranks them into `audienceQuestions`. `planNextCall` takes one from
`apify.topAudienceQuestions` and calls `apify.markAudienceQuestionUsed`.

## Build order

| Slice | What works at the end | Context the call uses |
|---|---|---|
| **1 · Onboarding** | Start call → Cartesia call → transcript → profile + story seeds | LinkedIn background (optional) |
| **2 · Story call + post** | Weekly call → post handed to `linkedapi.createPost` | Profile, story seeds, recent call summaries |
| **3 · Memory + feedback** | Vector memory, reader feedback, audience questions in the plan | Everything above + memories, comments, audience questions |

## Data model

`posts` and `audienceQuestions` are in `schema.ts`. Slice 1 adds the optional `elders` and
`calls` fields below. Everything else is still a draft.

```ts
elders: + stage?: "onboarding" | "active"      // missing = onboarding
        + linkedinUrl?, timezone?
        + profile?: { industry, specialty, careerSummary, topics[], storySeeds[], topicsToAvoid[] }
        (later: callDay, callHour)

calls:  callSid -> optional (v1 only)
        + kind?, cartesiaCallId?, summary?, endReason?, pollAttempts?, processedAt?
        index by_cartesia

memories (slice 3): elderId, callId?, text, embedding (1536), vectorIndex by elderId
engagement (slice 3): elderId, postId?, linkedinUrl, reactions, comments[], scrapedAt
```

**v1 leftovers in `convex/`**: `questions.ts`, `answers.ts`, `replies.ts` (and their tables)
belong to the old product; delete them. `elders.ts`, `calls.ts`, `lib/auth.ts` take a `secret`
argument from the deleted Python server; convert to internal functions. (Core: Data.)

## Going live

1. `npm run deploy` (`npx convex deploy`) creates/updates **production** (separate data + env).
2. Set every env var below on production (`npx convex env set` with `--prod`).
3. `npx convex run --prod cartesia:syncAgent` so the production agent matches the code.
4. Add production grandpa. Run onboarding → story call → post → scrape. Record a backup video.
